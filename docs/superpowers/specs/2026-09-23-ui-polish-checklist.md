## 登录

### 【登录】主按钮与 tab 同名、层级弱
- 现状：登录页同屏出现三个「登录」字样——顶部 tab「登录」、tab「注册」、底部提交按钮「登录」；且提交按钮为右下角蓝色文字按钮，视觉重量不如同页输入框，首次进入容易点错 tab（自动化走查时也误点过）。截图：`login-light.png` / `login-filled-light.png`
- 改法：tab 改分段控件样式（选中态实底）；提交按钮改**全宽 48dp 主色实心、圆角 8dp**，文案保留「登录」；按钮与 tab 间距 16dp
- 归类：打磨

### 【登录】「服务器地址」默认展开占位
- 现状：表单自上而下为 服务器地址 / 用户名 / 密码 三框，服务器地址对普通用户是无效信息，白占一行并把主表单推低（实测三框 y=467/566/644）
- 改法：默认只显示 用户名/密码；「服务器地址」收进可展开的「连接设置」小字链接（自部署场景才展开），展开态记住选择
- 归类：打磨

## 首页

### 【首页】状态卡统计环语义不明
- 现状：服务器状态卡每项指标（CPU/内存/磁盘剩余）数字下方画着一圈**不完整的圆环**（CPU 5% 几乎空环、内存半环、磁盘小段弧），无百分比标注，视觉上像「加载未完成」；截图：`home-light.png`
- 改法：二选一——① 圆环补全语义：浅色底环 + 品牌色弧 = 真实占比 + 环心/旁标注百分比；② 直接去掉圆环，数字下改 3dp 细进度条（下载/上传两列本来就是纯数字，保持一致更简洁）
- 归类：打磨

### 【首页】相册瓦片全占位图标、无照片封面
- 现状：首页「相册」区 3 块瓦片全部是通用占位图片图标（浅蓝底 + 图形），没有任何照片封面，看起来像加载失败；`最近` 列表图片行同样是默认图标。截图：`home-light.png`。注：本轮种子数据经 API 直传、可能确无封面，需用 UI 上传一张真实图片复核
- 改法：瓦片接 `ThumbnailLoader` 渲染封面（`clip(RoundedCornerShape(12dp))`、`ContentScale.Crop`）；复核后若服务端确无封面，瓦片区显示「上传照片后展示封面」的轻提示而非假图；图片行同 #7 一并处理
- 归类：打磨（关联审查清单 ④严重14：缩略图无磁盘缓存）

## 文件

### 【文件】面包屑路径条过重 🅰
- 现状：根目录/路径以**大号 chip 独占一行**（「根目录」蓝底圆角块，y=78 起、上下各留大片空白，一行吃掉约 40dp+ 外边距），列表首行被推到 y=132；进目录后 chip 与行列表风格脱节，太占空间（用户点名，要求像百度网盘那样简洁）。截图：`files-root-light.png` / 实机走查
- 改法：改**单行紧凑路径条**——14sp，左「‹ 返回上一级」（brand 色可点），右路径「父级 › 当前」（父级 brand 色可点、当前级 onSurface 加粗、超长中段 ellipsis），分隔符 `›` 8dp 间距；整行高 ≤36dp、上下各 4dp，紧贴顶栏下沿、页边距 16dp；删除现有 chip 样式。**参照基准：进目录后的「根目录 / 相册」文本链接样式（实机截图已确认）就是目标形态，根目录页对齐它即可，不需要发明新组件**
- 归类：打磨（用户点名·必修）

### 【文件】列表行高 68dp 超上限
- 现状：文件行 stride 实测 68dp（a11y box y=147/215/283/351），超 Global Constraints 行高 56–64dp 上限 4dp；桌面宽屏下整列偏松
- 改法：行内容垂直 padding 各收 2dp 至 **64dp**（含 1px 分割线），图标/文字基线不动
- 归类：打磨

### 【文件】图片文件行显示默认图标、无缩略图 🅰联动
- 现状：`应用封面.png` 等图片文件在**列表行与网格瓦片**中都显示通用图片图标，不是缩略图——OneDrive/百度网盘此场景均为小缩略图/封面；与用户点名的搜索缩略图（#9）同一根因、同一修法，建议一并勾选。截图：`files-root-light.png` / `files-grid-light.png`（网格瓦片同样为占位图标）
- 改法：图片类文件在**列表行、网格瓦片、搜索结果**三处统一改 `FileThumbnail`（列表 40dp 圆角 8dp / 网格瓦片整块封面 `Crop`），加载中渲染骨架块、失败回退现有图标；非图片文件保持扁平彩色分类图标
- 归类：打磨（用户点名联动）

### 【文件】暗色模式文件夹名黑字 —— ⚠ 本轮无法复现，待用户确认
- 现状（**与原报告不一致**）：1440×900 深色主题下逐一验证三处，全部**可读白字**，不构成缺陷——① 列表行 `FilesScreen.kt:1311`（无显式色，继承 `onSurface`）；② 网格单元 `:1067` 已显式 `color = onSurface`；③ 上传位置对话框 `:1858`。另：`grep` 全文件**无任何硬编码** `Color.Black/White/Color(0x…)` 文本色。截图：`files-wallpaper-dark.png`、`files-grid-dark.png`、`upload-location-dialog-dark.png`
- 改法：**先确认复现条件**（Android 原生端？「跟随系统 + 动态取色」？特定主题色？旧构建？）。若确能复现，再按 Task 7 给 `:1311`/`:1858` 显式补 `color = MaterialTheme.colorScheme.onSurface`；若不能复现，本条直接销项
- 归类：深色模式（**待复核**，原标记 🅱 降级）

## 搜索

### 【搜索】搜索结果图片不显示缩略图 🅰

### 【搜索】搜索期间无加载指示

- 改法：输入框下沿加 2dp 线性进度条（请求发出出现、结束消失），或结果区骨架行
- 归类：打磨

## 相册

- 现状：集合页点「全部照片」进入时间线后，内容区**完全空白**——无骨架屏、无空状态、无返回按钮，仅顶栏残留；等待 15 秒仍空白（实测 a11y 树 `list` 为空），随后页面自动弹回集合页。截图：`album-timeline-light.png`。注：审查清单 ④三态表声称时间线有 noPhotos 空态，与实测不符，需一并排查

### 【相册】集合瓦片巨大

### 【相册】时间线顶栏未见视图切换入口（待复核）

- 改法：复核后若确实缺失/藏得深——顶栏加 3 态图标分段控件（瀑布/均匀/日期），选中态品牌色底；若存在则统一其图标样式入清单增补

### 【预览】缩略图 404：根因是环境数据不一致，非 Web 鉴权问题 —— ✅ 环境已修复
- 原假设（已推翻，两次）：①「Web `<img>` 缺鉴权」——DOM 里**没有任何 `<img>`**，Compose Web 把图画在 canvas 上；②「客户端从不发请求」——我的 `fetch` 挂钩没抓到，因为 Ktor 在 wasm 上走 **XMLHttpRequest**（控制台 404 与服务端访问日志都证实请求确实发出）
- 真实根因：`/tmp` 被清导致 `thumbs/<sha>.jpg` 封面 blob 全丢，而 DB 里 `has_thumbnail` 仍为 `true`；GET 路由见标志为真就**跳过按需生成**、直接查 blob → 永久 `404 缩略图不存在`，列表/网格/首页瓦片/搜索全部退化成占位图标
- 修复（环境侧，无需改代码）：回填 5 个文件内容到 `blobs/` → 复位 `has_thumbnail=false` 触发服务端按需生成 → 再置回 `true`。随后首页瓦片、文件列表行、网格瓦片**全部显示真实缩略图**（`check-home-album-tiles.png`）
- 连带结论：**#4 首页瓦片占位图标**与 **#7 文件行无缩略图**同样由此引起，环境修复后已正常，**不需要改代码**
- 遗留代码加固（可选，建议排期）：GET 路由改为**先 `exists()` 再决定是否生成**，避免「标志与 blob 不一致」时永久 404
- 归类：**已解决（环境）**；加固项归打磨
